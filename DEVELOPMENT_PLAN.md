# План розробки MVP

Цей файл — робочий трекер прогресу. Онови статус (☐ → ☑) після кожного
завершеного етапу. Рекомендований підхід: не переходити до наступного
етапу, поки поточний не працює стабільно й видимо — це головний захист
від "розповзання" обсягу, про яке ми говорили на прикладі AFFiNE.

Кожен етап дає щось видиме й перевірне — це і є спосіб "вчасно
коригувати": якщо на якомусь етапі щось відчувається не так, це видно
одразу, а не після місяців роботи.

## Етап 0 — Підготовка проєкту

- [x] Ініціалізувати React Native проєкт (Expo — простіший старт для
      вайб-кодінгу, дозволяє тестувати через Expo Go без збірки)
- [x] Підключити Firebase проєкт (Spark/безкоштовний план), увімкнути

      увімкнено, Web-застосунок зареєстровано, SDK підключено в
      `src/firebase.ts` (конфіг береться з `.env`, див. `.env.example`)
- [x] Покласти `PROJECT_BRIEF.md` у корінь репозиторію
- [x] **Перевірка:** застосунок запускається на телефоні через Expo Go,
      показує порожній екран — підтверджено на реальному Android-пристрої
      користувача (SDK 57.0.0 співпав, застосунок відкрився); повторно
      підтверджено після підключення реальних Firebase-ключів через
      `.env` — застосунок ініціалізує Firestore/Auth при старті без
      помилок на екрані

## Етап 3 — Редактор документа (базові блоки)

- [x] Створення текстового блоку — одне Enter переносить рядок у тому
      самому блоці, друге Enter поспіль (на порожньому рядку) створює
      новий блок і переносить туди фокус (Android не передає інформацію
      про Shift навіть із фізичної клавіатури, тому Shift+Enter технічно
      недоступний — перевірено напряму в коді React Native)
- [x] Перетягування блоків для зміни порядку — саморобна реалізація на
      `react-native-gesture-handler`/`reanimated` (не бібліотека:
      `react-native-draggable-flatlist` мала непофіксовану несумісність
      із reanimated v4). Довге натискання будь-де на блоці; під час руху
      сам блок не рухається, лише тонка риска-індикатор плавно
      "примагнічується" між сусідніми блоками; перестановка масиву й
      "схлопування" старого місця відбувається один раз — при відпусканні
      пальця. Підтримує масове перетягування: у режимі виділення можна
      позначити кілька блоків і перетягнути їх усі разом
- [x] Виділення й видалення блоків — кнопка "виділити" в шапці вмикає
      режим із чекбоксами біля кожного блоку (замість свайпу — виявився
      ненадійним через конфлікт із текстовим полем); знизу з'являється
      кнопка "Видалити (N)" (якщо видалити останній блок — з'являється
      один порожній, щоб не лишати документ без структури)
- [x] Режим редагування — кнопка-олівець у шапці вмикає/вимикає
      можливість редагувати текст; поза цим режимом текстові поля
      "прозорі" для дотику, що дозволяє прокручувати аркуш свайпом з
      будь-якого місця (включно з текстом), а не лише через вузькі
      проміжки між блоками
- [x] Автозбереження у фоні — зміни заголовка й блоків пишуться в
      Firestore через 600мс після останньої зміни (з індикатором
      "Збереження…" / "Збережено" у шапці екрана)
- [x] **Перевірка:** написати документ із 5+ блоками (включно з
      багаторядковими), переставити їх місцями (поодинці й кількома
      виділеними разом), закрити й відкрити знову — все на місці —
      підтверджено користувачем на реальному пристрої

**Етап 3 завершено.**

## Етап 5 — Bypass-конвертація в об'єкти бази даних

За `PROJECT_BRIEF.md`: справи, нагадування, зображення, файли й посилання
є об'єктами бази даних **за замовчуванням** — без ручного кроку
"конвертувати" (той крок лишається тільки для майбутніх користувацьких
типів). Пілотним типом були **справи** (чекбокс-блок із текстом), за яким
підтягнулись **посилання**, **фото** й **файли**. Лишаються тільки
**нагадування**.

- [x] Справи: чекбокс-блок із непорожнім текстом автоматично дзеркалиться
      в колекцію Firestore `tasks` (`text`/`checked`/`documentId`);
      порожній текст, зміна типу блоку чи видалення блоку так само
      автоматично прибирає запис. Перегляд/перемикання виконано-не
      виконано — у вкладці "Більше" (`TasksScreen.tsx`), з проектами й
      "Сьогодні" — підтверджено на пристрої
- [x] Посилання: бланк-URL в абзаці автоматично стає карткою (YouTube/
      TikTok/Google Maps/загальні), дзеркалиться в `links`, ключ запису —
      сам URL (нормалізований), а не блок, тож те саме посилання з двох
      документів об'єднується в один запис зі списком документів, а не
      дублюється. Обов'язкове ім'я, якщо заголовок не підтягнувся сам.
      Підтверджено на пристрої (базовий сценарій); дедублікація і
      застрягле посилання після видалення — виправлено, ще не
      перетестовано на пристрої
- [x] Фото й файли: та сама схема, що й посилання (перелік документів,
      перейменування, що поширюється на всі картки), плюс сітка 2×2 для
      фото й повноекранний перегляд із діями (назва, документ, поділитись,
      завантажити, видалити). Щойно реалізовано, ще не підтверджено на
      пристрої
- [x] Теги — повна система: колекція Firestore `tags` (шлях "робота/оренда"
      через "/", іконка+колір, кумулятивний список типів, і `usedIn` — тег
      живе, лише поки на щось прикріплений, і видаляється сам, коли останнє
      прикріплення знято). Створення тега можливе тільки разом із першим
      присвоєнням (спливаюче меню з пошуком/автопідказками від 2 літер) —
      окремого екрана "створити тег" немає. Відео/гео/інші посилання
      поділяють одну колекцію `links`, але мають ОКРЕМІ пули тегів
      (`isTagAllowedForKind` у `useTags.ts`) — тег з відео не пропонується
      для гео чи інших посилань, і навпаки; файли/фото/посилання й далі
      вільно перетинаються між собою. Документи мають власний фіксований
      (не спливаючий) блок тегів під заголовком з інлайн-автопідказками
      (`DocumentTagsBlock`). Екран "Теги" (з хабу "Більше") — перегляд,
      перейменування й повне видалення тега. `TagItemsScreen` (список
      усього позначеного тегом + створити новий документ із ним одразу)
      лишається в коді й у навігації, але без активного входу з інтерфейсу
      відколи нижче описаний редизайн замінив вкладку "Пошук" шторкою
      тегів. Щойно реалізовано, ще не підтверджено на пристрої
- [x] Редизайн навігації під videobookmark-стиль: нижня панель вкладок
      прибрана — "Документи"/"Календар"/"Більше" тепер один плаваючий
      острівець (`FloatingIslandTabBar.tsx`, кастомний `tabBar` у
      `Tab.Navigator`); "Пошук" більше не вкладка, а іконка-лупа у
      верхньому правому куті "Документів", яка відкриває окремий екран
      пошуку за назвою документа (`SearchScreen.tsx`, перероблений з
      колишнього дерева/плиток тегів). Дерево/плитки тегів переїхали в
      `TagsDrawer.tsx` — шторку на 2/3 екрана, що витягується драгом за
      "язичок" зліва внизу (форма — половина острівця, той самий рівень).
      Вибір тега в шторці (чи пункту "Без тегів") фільтрує список
      документів на місці й закриває шторку; активний фільтр показаний
      чіпом під заголовком із хрестиком для скидання.
      Правки після першого раунду тестування на пристрої: шторка тепер
      малюється поверх острівця (вищий `elevation`/`zIndex`).
      Другий раунд — драг за язичок прибрано зовсім (він постійно
      конфліктував із жестом "назад" в Android і міг застрягати
      напівдорозі): замість нього окрема кругла кнопка внизу зліва
      (діаметр = висота острівця, стиль як острівець, піктограма "#"),
      тап по ній відкриває ту саму шторку. Анімація виїзду - швидка,
      без пружини/інерції (`withTiming` + `Easing.out`, а не `withSpring`,
      який "хитало як човен"), а темніння фону за шторкою окремо, трохи
      повільніше - той самий "не в фокусі" ефект без самого блюру.
      Справжній блюр (`expo-blur`, `experimentalBlurMethod=
      "dimezisBlurView"`) пробували - зламав застосунок у Expo Go
      ("Can't find ViewManager ExpoBlurView"): нативний модуль, який
      реально зашитий у клієнт Expo Go, не збігається версією з тим, що
      підтягнув npm, а це поза контролем з коду - тому від блюру
      відмовились, лишили звичайне (але з окремим таймінгом) затемнення.
      Закриття - тап по затемненій області, як і раніше.
      Заголовок "Бази даних" більше не заходить на статус-бар. Щойно
      реалізовано, ще не підтверджено на пристрої
- [x] Дрібні перестановки кнопок за фідбеком після тестування редизайну:
      у редакторі документа олівець (перемикач редагування) переїхав з
      верхнього рядка в плаваючу синю кнопку внизу праворуч (той самий
      функціонал); на його старому місці — заглушка "···" під майбутні
      функції, кружечок (режим виділення) лишився в рядку поруч. У хабі
      "Більше" (`DatabasesScreen`) теж додано заглушку "···" у верхньому
      правому куті. У Файлах/Фото/Посиланнях два стаб-значки
      сортування/фільтра замінені на одну лупу — робочий пошук по
      назві/файлу серед уже завантаженого списку (без окремого екрана).
      Щойно реалізовано, ще не підтверджено на пристрої
- [x] Картки документів у стилі YouTube-картки (за зразком videobookmark):
      рядок списку тепер зображення + текст замість простого рядка з
      іконкою. Ліворуч — перше зображення, вставлене в документ
      (`extractPreview` у `documentPreview.ts` шукає перший блок-картинку
      серед `blocks`); якщо картинок немає — біла плашка того самого
      розміру з піктограмою документа замість фото. Праворуч — жирний
      заголовок (до 2 рядків), під ним до 2 рядків тексту нотатки
      блідішим кольором (форматування `**bold**`/`{c:#hex}`/тощо знято —
      `stripFormatting`), внизу дата й час останньої редакції
      (`formatUpdatedAt`). Кошик для видалення лишився праворуч, як і
      раніше. Спільний компонент `DocumentCard.tsx` використовує і
      "Документи", і "Пошук".
      Окремо — повнотекстовий пошук: `SearchScreen` тепер шукає збіг не
      лише в заголовку, а й у тексті всередині блоків документа
      (`documentMatchesQuery`), і підсвічує знайдений фрагмент жовтим
      просто в картці результату (`findTitleMatch`/`findBodyMatch` дають
      шматок тексту навколо збігу, `DocumentCard` малює його як
      `<Text>` зі вкладеним підсвіченим `<Text>` — за зразком скріншота
      з Bear). Якщо збіг є в заголовку — підсвічується заголовок; інакше
      показується підсвічений уривок з тіла нотатки. Щойно реалізовано,
      ще не підтверджено на пристрої
- [x] Виправлено баг: шторка тегів насправді малювалась ПІД плаваючим
      острівцем (`elevation`/`zIndex` спрацьовує лише між прямими
      "сусідами" в одному й тому ж батьківському View, а острівець
      живе в геть іншій гілці дерева компонентів — його малює сам
      `Tab.Navigator`, а не `DocumentsScreen`). Виправлено переносом
      підложки й панелі шторки у справжній `Modal` (окреме системне
      вікно Android, завжди малюється поверх усього екрана незалежно
      від місця в дереві компонентів). Підтверджено на пристрої
- [x] **Екран "Календар"** (був заглушкою "Скоро"): тижнева стрічка
      Пн–Нд зі свайпом (звичайний paging `ScrollView` на 3 сторінки —
      попередній/поточний/наступний тиждень — замість власного
      drag-жесту, який раніше конфліктував із системним "назад" на
      Android); "сьогодні" — червоне коло, відкритий день — сіра
      рамка. Кнопка-шеврон під стрічкою розгортає повну сітку місяця
      (`LayoutAnimation.easeInEaseOut`, без Reanimated-пружини) з
      навігацією між місяцями. Дата зверху нотатки: повна назва дня
      тижня, число, короткий місяць, рік, номер тижня (ISO,
      понеділок-перший) — усе власними українськими масивами
      (`utils/dateLocale.ts`), а не `Intl`/`toLocaleString`, щоб не
      залежати від того, які дані ICU реально зашиті в Hermes на
      конкретному пристрої.
      Нотатка дня редагується просто на екрані календаря (як на
      референсі), без переходу нікуди — це той самий блоковий
      редактор, що і в звичайних документах (`DocumentEditorScreen`
      тепер приймає необов'язковий `embedded`-режим: ховає власний
      верхній рядок і поле заголовка, піднімає плаваючу кнопку
      олівця над острівцем, і замість `updateDoc` пише через
      `setDoc(..., {merge:true})`, бо документ дня при першому
      відкритті ще не існує в Firestore). Теги, зображення, файли,
      посилання — усе працює так само, бо нотатка дня це просто
      документ у тій самій колекції `documents` з доданим полем
      `calendarDate` ("YYYY-MM-DD"); "Документи" і "Пошук" відфільтровують
      такі документи, щоб вони не потрапляли у звичайний список.
      Перемикач "Показувати лише заповнені дні" (в меню "···",
      налаштування зберігається в `settings/calendarPrefs`) ховає
      число дня в сітці місяця для днів без реального вмісту —
      "заповненість" визначається за фактичним текстом/блоками
      (`hasNoteContent`), а не просто наявністю документа, інакше
      будь-який відкритий-але-не-заповнений день теж рахувався б
      заповненим.
      Правки після першого тесту на пристрої: (1) прибрано величезний
      пробіл між стрічкою днів і нотаткою — горизонтальний `ScrollView`
      у RN за замовчуванням має `flexGrow: 1`, тож стрічка розтягувалась
      на всю вільну висоту колонки (`flexGrow: 0` це лікує; той самий
      прийом уже був у `formatToolbar` редактора); (2) поки відкрита
      клавіатура, календар складається зовсім (стрічка/сітка/шеврон
      ховаються, дата стискається в один рядок із шевроном, який ховає
      клавіатуру) — інакше на телефоні від нотатки лишалась смужка
      висотою менше екранної клавіатури; (3) undo/redo та перемикач
      режиму виділення повернулись окремим тонким рядком над блоком
      тегів (плюс індикатор "Збережено"), бо у вбудованому режимі немає
      верхнього рядка редактора, з якого вони раніше працювали;
      (4) кнопка олівця піднімається над клавіатурою, коли та відкрита
      (інакше "готово" неможливо натиснути), а список отримав нижній
      відступ, щоб "Додати блок" не ховався за острівцем.
      Третій раунд: (1) баг "цифра попереднього дня зникає після
      натискання на інший" — це `LayoutAnimation` на Android:
      вона чіпляється до наступної ж зміни макета (у нас — зміна стилю
      числа при виборі дня) і лишає елемент назавжди прозорим.
      `LayoutAnimation` прибрано з календаря зовсім (у застосунку вона
      лишилась одна — на перестановці блоків, і там завжди йде реальна
      зміна макета, тож нічого "не зависає"); плюс кружечок дня тепер
      `View` з `Text` усередині, а рамка є завжди (просто прозора,
      коли не потрібна) — вибір дня більше взагалі не змінює жодного

      календар, коли з'являється клавіатура. Щойно реалізовано, ще не
      підтверджено на пристрої

## Свідомо відкладено на після MVP (не чіпати, поки Етап 9 не пройдено)

- **[Пріоритет №1 після MVP]** Резервне копіювання файлових блоків на
  Google Drive користувача — реальна інтеграція з Google Drive API (не
  Android Auto Backup, той обмежений 25МБ і потребує кастомної збірки
  поза Expo Go). Означає: другу систему авторизації (Google Sign-In,
  окремо від нинішнього Firebase Email/Password) і другий бекенд (Drive
  API — токени, оновлення токенів, завантаження/довантаження) —
  паралельна інфраструктура поруч із Firebase, тому й відкладено, а не
  зроблено одразу з файловими блоками. Мета: файл (і в перспективі
  фото) переживає видалення застосунку й видно у власному Google Drive
  користувача, довантажується після повторного входу.
- Дошка (канвас, рамка А4, магнітне групування)
- Довільні типи об'єктів, створювані користувачем
- Пов'язані бази даних (письменники ↔ книги)
- Веб-версія
- Візуальний щоденник з гортанням прев'ю
- Два екрани Fold (зовнішній/внутрішній) — MVP тестується як звичайний
  застосунок на одному екрані
